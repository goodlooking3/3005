# خطة رفع جاهزية الشاشات وتجربة المستخدم — 2026-10-04

## 1. فهم النطاق

المطلوب ليس التأكد من أن الشاشة تستدعي `Repository` فقط، بل التأكد من أن كل شاشة تمثل وظيفة النظام الموجودة في الخلفية بصورة كاملة ومهنية للمستخدم النهائي:

- لا تظهر أسماء ملفات أو استثناءات أو تفاصيل قاعدة البيانات أو رسائل تخص المطور.
- كل حقل موجود في نموذج المجال أو خدمة العملية ويحتاجه المستخدم يظهر في موضعه المناسب.
- كل زر موجود في الوظيفة الخلفية وله أثر للمستخدم يظهر بوضوح: حفظ، ترحيل، إلغاء، طباعة، مشاركة، تصدير، استيراد، تحديث، بحث، تصفية، عملة، تاريخ، أصناف، حسابات.
- كل عملية تعرض حالات التحميل، النجاح، الفشل، الفراغ، وإعادة المحاولة دون فقد المدخلات.
- كل شاشة تعمل على عرض الهاتف والكمبيوتر: لا overflow أفقي غير مقصود، ولا أزرار مختفية أو نماذج ضيقة أو جداول غير قابلة للاستخدام.
- لا تُضاف وظيفة شكلية غير مدعومة في الخلفية، ولا تعرض الشاشة نجاحًا أو اتصالًا لم تثبته الخدمة.

## 2. طريقة التدقيق لكل شاشة

لكل شاشة تُنفذ الخطوات التالية قبل اعتبارها جاهزة:

1. **جرد الخلفية:** تحديد النموذج، المستودع/الخدمة/المحرك، العمليات المتاحة، القيود، الحقول، العملات، التواريخ، وحالات السجل.
2. **جرد الواجهة:** مقارنة كل حقل وزر وفلتر وبحث وتبويب وتصدير/طباعة مع الجرد الخلفي.
3. **تدقيق السلوك:** تجربة الإدخال الصحيح، الإدخال الناقص، الفشل، الإلغاء، إعادة المحاولة، النقر المكرر، والعودة من الشاشة الفرعية.
4. **تدقيق البيانات:** التأكد أن القيم المعروضة من المصدر الفعلي وأن الرقم/العملة/الحالة/الرصيد مرتبط بالسجل الصحيح.
5. **تدقيق الاستجابة:** اختبار عرض ضيق للهاتف، عرض متوسط، وعرض سطح المكتب؛ معالجة `Overflow` وإعادة ترتيب الأفعال الثانوية.
6. **تدقيق اللغة:** استبدال رسائل `$exception` وعبارات المطور برسائل عربية مفهومة، مع الاحتفاظ بالتفاصيل في سجل التدقيق فقط عند الحاجة.
7. **اختبار قابل للتكرار:** إضافة أو تحديث اختبار Widget/تكامل لكل فجوة مهمة، ثم تشغيل CI قبل الانتقال.

## 5. قواعد الرسائل للمستخدم

- ممنوع عرض `catch (error) => '$error'` في الشاشة عندما يحتوي الخطأ على اسم ملف أو SQL أو stack trace.
- تُحوّل الأخطاء إلى رسائل عربية عملية مثل: «تعذر حفظ الفاتورة. تحقق من الحساب والعملة والكمية ثم حاول مجددًا».
- رسائل النجاح تذكر النتيجة الفعلية: رقم السند/الفاتورة، عدد السجلات، أو ما إذا كان الترحيل تم.
- لا تُعرض حالة «متصل» أو «مرحّل» إلا بعد نتيجة الخدمة وقيد/سجل قابل للتتبع.
- كل زر عملية غير قابل للتكرار أثناء التنفيذ ويُعاد تمكينه بعد النجاح أو الفشل.

## 6. تعريف الانتهاء

لا تُعتبر الشاشة مكتملة إلا عند تحقق جميع البنود التالية:

- تطابق 100% بين الوظيفة الخلفية والحقول/الأفعال اللازمة للمستخدم.
- لا توجد معلومات مطور أو أخطاء تقنية في الواجهة.
- حالات التحميل، الفشل، الفراغ، النجاح، والإلغاء واضحة.
- الهاتف والكمبيوتر قابلان للاستخدام دون قص أو overflow أو اختفاء الأفعال الأساسية.
- اختبار Widget أو تكامل يغطي المسار الرئيسي وحالة الفشل المهمة.
- فحوص طول الملفات وربط الشاشات والتحليل والاختبارات وبناء Web review ناجحة.
- تحديث سجل الجلسة ودفع الالتزام إلى `main` قبل بدء المرحلة التالية.

## 7. ترتيب التنفيذ التالي

1. إكمال تدقيق فاتورة البيع والمرتجعات: الحقول، العملة، الحسابات، المخزون، الإجمالي، الطباعة/المشاركة، والاستجابة.
2. إكمال تدقيق المشتريات وتسويات checkout على الهاتف والكمبيوتر.
3. إضافة طبقة رسائل مستخدم موحدة وإزالة تفاصيل الاستثناءات من الشاشات.
4. تدقيق المحاسبة والتقارير والتصدير/الطباعة.
5. تدقيق الموصلات والمحفظة ثم الإعدادات والنسخ.
6. تشغيل بوابة قبول نهائية وتحديث قرار Go/No-Go.

### تعريف انتهاء دورة الحسابات

لا تُعتبر هذه الدورة مكتملة إلا بعد إثبات أن الحساب والطرف والسند يستخدمون المعرفات الفعلية لا الاسم النصي فقط، وأن قاعدة البيانات تحفظ `account_id` للطرف و`party_id` لسطر القيد، مع ترقية آمنة للبيانات القديمة، واختبار تكامل يثبت الإنشاء والربط والترحيل ورفض الربط غير المتوافق على الهاتف والكمبيوتر.


## 9. ملاحظة المستخدم المعتمدة — شاشات مستقلة للحسابات والمحفظة

تُضاف هذه المتطلبات إلى الخطة باعتبارها دورة تنفيذ مستقلة، وليست عناصر فرعية داخل شاشة «دليل الحسابات»:

- شاشة مستقلة لإدارة الحساب الرئيسي والحساب الأب والحساب الفرعي والحساب التحليلي، مع الترقيم، منع التكرار والدورات، الأسماء بالعربي والإنجليزي، الأب، الحساب التجميعي/الترحيلي، وتفعيل/إيقاف الحساب.
- شاشة مستقلة لإضافة وتعديل الحساب التحليلي/العميل/المورد، ترتبط بمعرف الحساب الفعلي لا الاسم النصي، وتعرض الاسم العربي والإنجليزي، العملة، العملات المسموحة وفق صلاحية الحساب، السقف الائتماني، العنوان، الهاتف، والحالة.
- العملات اختيار متعدد للحساب بحسب الصلاحيات؛ لا يُفرض فلتر عملة واحدة على شاشة الإدخال. تبقى العملة الأساسية للترحيل واضحة، وتُرفض المعاملة فقط إذا لم تكن العملة ضمن قائمة الحساب المسموحة.
- ربط الحسابات التحليلية بدليل الحسابات وقاعدة SQLite والمنطق المحاسبي، مع حفظ `account_id` للطرف و`party_id` لسطور القيود وترقية آمنة للبيانات القديمة.
- اعتماد شاشة «محفظتي/الصندوق» المستقلة لإدارة المحفظة أو الصندوق وحساباته، وربط كل حساب محفظة بحساب نقدي/بنكي محاسبي وبالعملة، مع الحركات والتصفية والترحيل وحالات النجاح والفشل.
- معيار قبول إضافي: لا تُعد هذه الوظائف مكتملة إذا كانت مجرد تبويب أو حوار داخلي بلا مسار شاشة مستقل قابل للفتح والتحديث والعودة، أو إذا ظهرت بيانات تجريبية/عملة مفروضة لا يملكها الحساب.

### مخرجات التنفيذ الحالية

- أضيفت شاشة `AccountManagementScreen` لإدارة الشجرة مستقلة، وشاشة `AnalyticalAccountsScreen` للحسابات التحليلية والعملاء والموردين.
- أضيفت حقول الأسماء الثنائية للحساب، وحقول الاسم العربي/الإنجليزي والعنوان والهاتف والسقف والحالة للطرف، مع مهاجرة SQLite إلى الإصدار 27.
- شاشة المحفظة الحالية مستقلة أصلًا. أضيف إليها إجراء لإلحاق حساب نقدي/بنكي تفصيلي نشط، مع اختيار عدة عملات من قائمة العملات المسموحة للحساب وحفظ جميع روابط العملات في معاملة واحدة. لا تعدّل هذه الخطوة أرصدة أو قيودًا سابقة.
- لا يزال تحرير/تعطيل الروابط القائمة واستيراد/تصدير كشف المحفظة والقبول البصري الشامل للهاتف والكمبيوتر ضمن العمل اللاحق.

## 10. تنفيذ إدارة حسابات المحفظة والعملات — 2026-10-04

- أضيف إجراء من شاشة «محفظتي» ومن بطاقة كل محفظة لإلحاق حساب محاسبي موجود بدل إنشاء ربط اسمي غير قابل للتحقق.
- يعرض الاختيار الحسابات التفصيلية النشطة من نوع نقد/بنك فقط، وتُشتق العملات من `account_currencies` (مع العملة الأساسية كحل رجوع عند غياب سجلات العملات).
- يدعم ربط الحساب نفسه بعدة عملات مسموحة؛ ينشئ النظام صفًا لكل عملة في `wallet_accounts` ويربط كل صف بمعرف الحساب الفعلي.
- يتحقق المستودع مجددًا من نشاط الحساب ونوعه وكونه تفصيليًا ومن صلاحية العملة، ويحفظ مجموعة الروابط ذريًا؛ رفض أي عملة يمنع حفظ المجموعة جزئيًا.
- استُبدل تخطيط بطاقات المحفظة ذي النسبة الثابتة بقائمة مرنة لتفادي قصّ البطاقة عند زيادة عدد العملات أو على عرض الهاتف.
- أضيف اختبار تكامل للحفظ متعدد العملات واختبار رفض عملة غير مسموحة مع إثبات عدم بقاء صفوف جزئية. التحليل/الاختبارات والبناء ولقطة الهاتف ما زالت بانتظار بوابة CI والقبول البصري.
