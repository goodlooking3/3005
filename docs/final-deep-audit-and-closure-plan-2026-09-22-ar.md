## الحكم التنفيذي

المشروع **قابل للتشغيل البرمجي على مستوى الاختبارات المحلية**، لكنه **ليس جاهزًا بعد لإعلان الإغلاق النهائي أو البناء الإنتاجي بنسبة 100/100**. النتيجة المحايدة الحالية هي **72/100**، مع تفاوت واضح بين الوحدات. هذا التقييم لا يعني أن المشروع غير صالح؛ بل يعني أن بعض وظائف الأعمال الأساسية تعمل، بينما ما زالت هناك فجوات في الذرية المحاسبية، وتعدد العملات، واعتماد أجهزة Windows وAndroid الحقيقية، وبوابة CI الإنتاجية.

يوصى بإيقاف البناء الإنتاجي إلى أن تُغلق عوائق P0 الموضحة في هذا التقرير. يمكن بعد ذلك تنفيذ بناء تجريبي، ثم اختبار قبول يدوي، ثم إعلان الإغلاق النهائي إذا نجحت جميع البوابات.

## النتائج المانعة للإغلاق النهائي

### 1. عدم ذرية الشراء بين القيد والمخزون

`PurchaseEngine.checkout` يستدعي `ledger.post` أولًا، ثم ينفذ حفظ أمر الشراء وتحديث المخزون في عملية منفصلة. إذا نجح القيد وفشل حفظ أمر الشراء أو حركة المخزون، يمكن أن يبقى قيد شراء بلا أمر شراء أو بلا أثر مخزني كامل. هذا خطر محاسبي وتشغيلي من مستوى P0.

**المطلوب:** نقل ترحيل القيد وأمر الشراء وحركة المخزون إلى transaction SQLite واحدة، أو توفير جسر محاسبي يقبل `Transaction` ويكتب كل أجزاء العملية داخلها.

### 2. عدم ذرية حفظ حركة المحفظة

`WalletRepositoryImpl.saveTransaction` يرحل القيد أولًا عبر `AccountingLedgerBridge`، ثم يحفظ سجل `wallet_transactions` في عملية مستقلة. الفشل بين المرحلتين ينتج قيدًا بلا حركة محفظة مقابلة.

**المطلوب:** توحيد القيد وسجل المحفظة في transaction واحدة مع اختبار فشل متعمد يثبت rollback الكامل.

### 3. تعدد العملات غير مكتمل محاسبيًا

تمت إضافة `currencies` و`exchange_rates` و`CurrencyRepository`، لكن العمليات لا تفرض بعد ما يلي بشكل موحد:

- أن تكون العملة ضمن جدول العملات النشطة.
- أن تتوافق عملة الصنف مع عملة الفاتورة أو أن يطبق تحويل معلن.
- حفظ قيمة العملية بالعملة الأصلية والعملة الأساسية.
- تسجيل سعر الصرف المستخدم داخل المستند.
- احتساب فروق الصرف عند التحويل أو التسوية.
- ربط العملة بحساب العميل أو المورد أو المحفظة قبل الترحيل.

توجد مخاطرة واضحة في شاشة البيع الحالية: يمكن اختيار عملة فاتورة تختلف عن عملة الصنف دون تطبيق تحويل سعر صرف.

**المطلوب:** اعتماد سياسة عملة مركزية تمنع الترحيل غير المتوافق وتخزن سعر الصرف والقيمة الأساسية لكل مستند مالي.

### 4. بوابة GitHub Actions الأساسية غير متوافقة مع نتيجة التحليل الحالية

ملف `.github/workflows/flutter.yml` يشغل `flutter analyze` دون `--no-fatal-infos`. التحليل الحالي يحتوي على 28 ملاحظة `info`، بينما ينجح باستخدام `--no-fatal-infos`. لذلك يجب اختيار سياسة واحدة قبل الإغلاق:

- إصلاح جميع الملاحظات ثم إبقاء التحليل صارمًا.
- أو اعتماد `--no-fatal-infos` في بوابة CI مع إبقاء الأخطاء والتحذيرات المانعة.

لا يجوز إعلان أن CI مغلق قبل نجاح التشغيل الفعلي على GitHub Actions في المستودع الجديد.

### 5. الاختبار اليدوي والبصري على Windows وAndroid لم ينفذ

اختبار الدخان يثبت أن الشاشات تُبنى دون استثناءات في بيئة الاختبار، لكنه لا يثبت:

- صحة الخطوط العربية واتجاه RTL على Windows وAndroid.
- عمل الإشعارات وصلاحيات Notification Listener على Android الحقيقي.
- عمل File Picker والطباعة وPDF والنسخ الاحتياطي على Windows.
- قابلية القراءة والتفاعل على مقاسات الشاشات المختلفة.
- نجاح حزمة Android الموقعة وتثبيتها.
- نجاح مثبت Windows وتشغيل SQLite في بيئة مستخدم حقيقية.

### 6. التغطية غير كافية لإعلان 100/100

التغطية الحالية 39.38%. الملفات ذات الفجوات الأكبر تشمل `main.dart`، وخدمة التصدير، وشاشة المردودات، ومستودع المحاسبة، وشاشة فاتورة البيع الجديدة، ومستودع المحافظ. يجب رفع تغطية مسارات الأعمال الحرجة، لا مجرد رفع الرقم العام.

## نتائج إيجابية مؤكدة

قاعدة البيانات الموحدة تعمل عبر SQLite وملف `wasel.db`، ولم يظهر استخدام Hive أو Isar أو Drift أو قاعدة موازية في مسارات التطبيق المفحوصة. توجد هجرات حتى الإصدار 14، وتوجد اختبارات للتحقق من سياسة SQLite.

محرك البيع يستخدم transaction واحدة لكتابة القيد، وتحديث المخزون، وحفظ الفاتورة، وتسجيل حركة المخزون. كما توجد اختبارات للبيع والمرتجع الجزئي والكامل والإلغاء وتجاوز الكمية.

نافذة سندات القبض والصرف القديمة ما زالت هي نقطة الدخول الأصلية. تم تحسينها داخل `main.dart` لتستخدم البحث في الحسابات والأطراف واختيار العملة، ولم تُنشأ شاشة بديلة لها.

حواجز طول الملفات وربط الشاشات وقاعدة SQLite ناجحة. الملفات التي تتجاوز 500 سطر محصورة في الاستثناءين القديمين والملفات التي لا تتجاوزهما الشيفرة الجديدة.

## خطة الإغلاق التكميلية المقترحة

### المرحلة P0: سلامة البيانات والـ CI

1. جعل الشراء عملية ذرية تشمل القيد وأمر الشراء والمخزون والحركة.
2. جعل حركة المحفظة عملية ذرية تشمل القيد وسجل المحفظة.
3. توحيد التحقق من الحسابات والأطراف والعملات قبل الترحيل.
4. إصلاح بوابة `flutter.yml` ثم تشغيلها فعليًا على المستودع الجديد.
5. إضافة اختبارات rollback لكل عملية متعددة الجداول.

**بوابة الخروج:** لا توجد سجلات يتيمة عند فشل أي خطوة، وCI أخضر بالكامل.

### المرحلة P1: إغلاق المحاسبة متعددة العملات

1. إضافة سياسة عملة مركزية للحسابات والأطراف والمحافظ والفواتير.
2. منع اختلاف عملة الصنف والفاتورة دون سعر صرف صالح.
3. حفظ سعر الصرف والقيمة الأساسية داخل مستندات البيع والشراء والسندات والمحافظ.
4. إضافة اختبار تحويل وفروق صرف وتسوية متعددة العملات.

**بوابة الخروج:** كل مستند مالي يملك عملة أصلية وقيمة أساسية وسعر صرف قابلًا للتدقيق عند الحاجة.

### المرحلة P2: إغلاق الحقول والمسارات التشغيلية

1. اختبار سند القبض والصرف والقيد اليومي بعميل ومورد وحسابات مختلفة.
2. منع الترحيل عند حساب غير موجود أو حسابين متساويين أو طرف غير صالح.
3. اختبار إضافة حساب وإضافة عميل وإضافة مورد ثم استخدامهما في السند.
4. اختبار دورة شراء كاملة: اختيار مورد، إضافة منتج، دفع، استلام، تحديث المخزون، ثم البيع.
5. اختبار دورة البيع كاملة: بحث عميل، اختيار صنف، خصم المخزون، القيد، المرتجع، والإلغاء.
6. تحديد نطاق الضريبة والخصم والمسودة قبل اعتبارها ميزات إنتاجية أو توثيق استبعادها رسميًا.

**بوابة الخروج:** كل حقل ظاهر له أثر خلفي قابل للإثبات، ولا توجد أزرار أعمال حرجة بلا معالج فعلي.

### المرحلة P3: رفع جودة الاختبارات

1. إضافة اختبارات واجهة مباشرة لنافذة سند القبض والصرف القديمة.
2. إضافة اختبار واجهة كامل لشاشة فاتورة البيع الجديدة.
3. رفع تغطية الخدمات الحرجة إلى 80% على الأقل، مع تغطية مسارات الفشل لا مسارات النجاح فقط.
4. اختبار الترحيل المكرر، وفشل الشبكة، وإعادة المحاولة، وقاعدة بيانات قديمة من كل إصدار رئيسي.
5. فصل اختبارات الأداء عن بوابة الاختبارات السريعة أو ضبط ميزانية موثقة لها.

**بوابة الخروج:** تغطية مسارات P0 وP1 كاملة، وتغطية عامة لا تقل عن 80% للشيفرة الإنتاجية القابلة للاختبار.

### المرحلة P4: اعتماد الأجهزة والإصدار

1. تشغيل Android Actions مع أسرار التوقيع ونتيجة APK واضحة.
2. تثبيت APK على جهاز Android حقيقي واختبار الإشعارات والصلاحيات وRTL وSQLite.
3. تشغيل Windows Actions وتثبيت Setup على Windows حقيقي واختبار SQLite وPDF وFile Picker والنسخ الاحتياطي.
4. تنفيذ اختبار قبول يدوي موثق لكل شاشة ووحدة.
5. إنشاء release candidate ثم اختبار ترقية قاعدة بيانات من نسخة أقدم.
6. بناء الإصدار النهائي فقط بعد اعتماد بوابات P0 إلى P4.

**بوابة الخروج:** توقيع ناجح، تثبيت ناجح، اختبار قبول ناجح، وعدم وجود عائق إنتاجي مفتوح.
