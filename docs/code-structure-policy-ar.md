# سياسة بنية كود مشروع واصل

## اللغة والمنصة وقاعدة البيانات

يُطوّر المشروع بلغة **Dart** وبإطار **Flutter** فقط. تستخدم جميع طبقات التخزين قاعدة **SQLite** عبر `sqflite` أو `sqflite_common_ffi` للاختبارات. لا تُضاف قاعدة بيانات ثانية أو طبقة تخزين بديلة دون قرار معماري موثق.

## حد طول الملفات

يجب ألا يتجاوز أي ملف Dart جديد أو معدل **500 سطر**. يبدأ التحذير عند **400 سطر** حتى لو لم تقع مخالفة بعد، ويُمنع تجاوز 500 سطر إلا للاستثناءات القديمة الموثقة. يتحقق GitHub Actions من ذلك عبر `tool/check_file_lengths.dart`.

توجد ثلاثة ملفات قديمة تتجاوز الحد، ومجمدة مؤقتًا لتجنب كسر العقود العامة أثناء الإغلاق الأول:

- `lib/main.dart`
- `lib/app_shell_part.dart`
- `lib/data/accounting_repository.dart`

لا يجوز إضافة وظيفة جديدة إليها. أي وظيفة جديدة يجب أن توضع في ملف Dart مستقل، ويجب مراجعتها عند بلوغ 400 سطر، ولا تتجاوز 500 سطر. `app_shell_part.dart` يجمع callbacks تشترك في حالة StatefulWidget واحدة؛ يلزمه تفكيك سلوكي مستقل قبل إزالة الاستثناء. تبدأ إعادة الهيكلة اللاحقة بنقل الوحدات الداخلية إلى `presentation`, `application`, `data`, و`domain`، ثم تصبح الاستثناءات الثلاثة فارغة.

## قواعد الإضافة الجديدة

يجب أن يملك كل ملف جديد مسؤولية واحدة قابلة للاختبار. يجب فصل الشاشة عن controller وعن repository. يجب ألا تستدعي الواجهة SQL مباشرة إذا كانت العملية جزءًا من منطق أعمال قابل لإعادة الاستخدام. يجب أن تمر عمليات SQLite متعددة الخطوات عبر transaction واحدة.

قبل الدمج يجب تشغيل:

```bash
flutter analyze
flutter test --concurrency=1
flutter pub run tool/check_file_lengths.dart
```

لا يُسمح بتجاوز الحارس عبر تعديل الاستثناءات إلا في commit معماري يضيف سببًا وتاريخًا وخطة تفكيك.
